## 1. PRD 개요

### 1.1 제품 목적

`notice-project`는 공지사항(Notice)을 등록·조회·수정·삭제할 수 있는 가장 단순한 웹 애플리케이션이다.

핵심 설계는 다음과 같다.

- Spring Boot는 CRUD와 PostgreSQL 데이터 접근만 담당한다.
- 검색과 페이징은 Spring Boot에서 처리하지 않고 Vue 3에서 처리한다.
- 백엔드는 `GET /api/notices`로 전체 목록을 반환한다.
- 상세 조회 시 백엔드가 조회수(`hits`)를 1 증가시킨다.
- 프런트엔드는 Axios + Pinia + Vue Router + Tailwind CSS를 사용한다.
- 모든 화면은 Vue Single File Component와 `<script setup>`으로 작성한다.
- 초기 버전에서는 로그인/권한/댓글/첨부파일을 넣지 않는다.
- 향후 데이터가 많아지면 서버 검색/페이징으로 교체할 수 있도록 계층과 API를 단순하게 유지한다.

### 1.2 문제 정의

학습용 게시판은 기능이 많아질수록 검색·페이징·회원·권한·댓글 등의 코드가 빠르게 복잡해진다. 이 프로젝트는 우선 CRUD와 클라이언트 검색/페이징만 구현하여 전체 애플리케이션 흐름을 짧은 시간 안에 이해하고, 이후 기능을 단계적으로 확장할 수 있도록 한다.

### 1.3 제품 목표

1. 개발자가 요구사항을 짧은 AI 프롬프트만으로 재생성할 수 있을 만큼 요구사항을 명확히 한다.
2. 백엔드와 프런트엔드의 책임을 분리한다.
3. CRUD의 기본 흐름을 모두 구현한다.
4. 검색과 페이징의 동작 원리를 Vue에서 쉽게 이해할 수 있도록 한다.
5. 나중에 서버 페이징, 인증, 회원, 관리자 기능을 추가해도 구조를 크게 깨지 않도록 한다.

### 1.4 범위 밖

다음 기능은 1차 버전에서 제외한다.

- Spring Security / 로그인
- 회원/역할 관리
- 첨부파일
- 댓글/대댓글
- 좋아요
- 공지 고정
- 서버 검색
- 서버 페이징
- 전문 검색
- 캐시
- 감사 로그
- 배치 처리
- 다국어
- 실시간 알림

## 2. 사용자와 사용 시나리오

### 2.1 주요 사용자

| 사용자 | 설명 |
|---|---|
| 일반 사용자 | 공지사항을 목록으로 보고 검색하고 상세 내용을 확인한다. |
| 작성 사용자 | 공지사항을 등록하고 수정하고 삭제한다. |
| 개발자/학습자 | 전체 프로젝트를 이해하고 AI와 함께 코드를 수정/확장한다. |

### 2.2 핵심 사용자 시나리오

#### 시나리오 A — 목록 확인
1. 사용자가 `/notices`에 접속한다.
2. Vue가 `GET /api/notices`를 호출한다.
3. 전체 공지사항을 Pinia store에 저장한다.
4. 화면에서 제목/내용/작성자 기준 검색이 가능하다.
5. 검색 결과를 10건 단위로 페이징한다.

#### 시나리오 B — 상세 확인
1. 사용자가 제목을 클릭한다.
2. Vue가 `/notices/{id}`로 이동한다.
3. `GET /api/notices/{id}`를 호출한다.
4. 백엔드는 조회수를 1 증가시킨다.
5. 증가된 조회수를 포함한 상세 정보를 반환한다.

#### 시나리오 C — 등록
1. 사용자가 `/notices/new`에 접속한다.
2. 제목/내용/작성자를 입력한다.
3. Vue가 `POST /api/notices`를 호출한다.
4. 성공하면 상세 또는 목록 화면으로 이동한다.

#### 시나리오 D — 수정
1. 사용자가 상세 화면에서 수정 버튼을 클릭한다.
2. Vue가 수정 화면을 표시한다.
3. `PUT /api/notices/{id}`를 호출한다.
4. 성공하면 최신 상세 화면으로 이동한다.

#### 시나리오 E — 삭제
1. 사용자가 상세 화면에서 삭제를 클릭한다.
2. 사용자에게 확인을 요청한다.
3. `DELETE /api/notices/{id}`를 호출한다.
4. 성공하면 목록으로 이동한다.

## 3. 핵심 기능 요구사항

### FR-01 전체 목록

- 엔드포인트: `GET /api/notices`
- 응답: 전체 Notice 목록
- 정렬: 최신 `id` 우선
- 검색 파라미터: 사용하지 않는다.
- 페이지 파라미터: 사용하지 않는다.
- 프런트엔드가 검색과 페이징을 수행한다.

### FR-02 상세 조회

- 엔드포인트: `GET /api/notices/{id}`
- 존재하지 않는 ID는 404를 반환한다.
- 상세 조회가 성공하면 `hits`를 1 증가한다.
- 응답에는 증가된 조회수를 포함한다.

### FR-03 등록

- 엔드포인트: `POST /api/notices`
- 필수값: `title`, `content`, `author`
- 등록 시 `id`는 DB가 생성한다.
- `hits` 기본값은 0이다.
- `createdAt`은 백엔드에서 생성한다.

### FR-04 수정

- 엔드포인트: `PUT /api/notices/{id}`
- 필수값: `title`, `content`, `author`
- `id`, `hits`, `createdAt`은 클라이언트가 임의로 변경하지 않는다.
- 존재하지 않는 ID는 404를 반환한다.

### FR-05 삭제

- 엔드포인트: `DELETE /api/notices/{id}`
- 존재하지 않는 ID는 404를 반환한다.
- 성공 시 `204 No Content`를 반환한다.

### FR-06 클라이언트 검색

검색 대상:

- `title`
- `content`
- `author`

검색 방식:

- 대소문자를 구분하지 않는다.
- 빈 문자열이면 전체 목록을 표시한다.
- 검색어가 바뀌면 1페이지로 돌아간다.
- 검색 결과가 없으면 빈 결과 안내를 표시한다.

### FR-07 클라이언트 페이징

기본값:

- 페이지 크기: 10
- 현재 페이지: 1

처리 방식:

```text
전체 목록
   ↓
검색 필터
   ↓
filteredNotices
   ↓
페이지 크기 10
   ↓
slice(start, end)
   ↓
현재 페이지 출력
```

URL query 예시:

```text
/notices?keyword=서비스&page=2
```

브라우저 새로고침 후에도 검색어와 현재 페이지를 복원한다.

### FR-08 입력 검증

프런트엔드:

- title: 공백 불가, 최대 200자
- content: 공백 불가
- author: 공백 불가, 최대 50자

백엔드:

- 동일한 수준의 최소 검증을 `jakarta.validation`으로 수행한다.

## 4. 데이터 모델

### 4.1 Notice

| 필드 | Java 타입 | DB 개념 | 필수 | 설명 |
|---|---|---|---|---|
| id | Long | BIGINT PK | O | 자동 증가 PK |
| title | String | VARCHAR(200) | O | 공지 제목 |
| content | String | TEXT | O | 공지 내용 |
| author | String | VARCHAR(50) | O | 작성자 |
| hits | Long | BIGINT | O | 조회수 |
| createdAt | LocalDateTime | TIMESTAMP | O | 등록일시 |

### 4.2 테이블

```sql
CREATE TABLE notice (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    content TEXT NOT NULL,
    author VARCHAR(50) NOT NULL,
    hits BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL
);
```

실제 운영에서는 DDL을 직접 관리하는 migration 도구로 변경할 수 있지만, 1차 학습 버전은 JPA `ddl-auto: update`를 사용한다.

## 6. API 명세

### 6.1 공통 규칙

- Base URL: `/api`
- Content-Type: `application/json`
- 날짜 포맷: ISO-8601 LocalDateTime
- 오류 응답은 JSON으로 반환한다.

오류 예:

```json
{
  "status": 404,
  "message": "공지사항을 찾을 수 없습니다."
}
```

### 6.2 API 표

| Method | URL | 설명 | 성공 |
|---|---|---|---|
| GET | `/api/notices` | 전체 목록 | 200 |
| GET | `/api/notices/{id}` | 상세 조회 + 조회수 증가 | 200 |
| POST | `/api/notices` | 등록 | 201 |
| PUT | `/api/notices/{id}` | 수정 | 200 |
| DELETE | `/api/notices/{id}` | 삭제 | 204 |

### 6.3 목록 응답

```json
[
  {
    "id": 2,
    "title": "서비스 이용 안내",
    "content": "공지사항 내용",
    "author": "관리자",
    "hits": 5,
    "createdAt": "2026-09-22T08:30:00"
  }
]
```

### 6.4 등록 요청

```json
{
  "title": "서비스 점검 안내",
  "content": "9월 30일 점검 예정입니다.",
  "author": "관리자"
}
```

### 6.5 수정 요청

```json
{
  "title": "서비스 점검 안내(수정)",
  "content": "점검 시간이 변경되었습니다.",
  "author": "관리자"
}
```

### 6.6 상태 코드

| 상태 | 의미 |
|---|---|
| 200 | 조회/수정 성공 |
| 201 | 등록 성공 |
| 204 | 삭제 성공 |
| 400 | 입력값 오류 |
| 404 | 대상 데이터 없음 |
| 500 | 서버 오류 |

## 10. 비기능 요구사항

### NFR-01 단순성

- 불필요한 라이브러리를 추가하지 않는다.
- 백엔드 검색/페이징 코드를 넣지 않는다.
- REST API와 화면 책임을 분리한다.

### NFR-02 확장성

다음 확장이 가능한 구조를 유지한다.

```text
현재
GET /api/notices

향후
GET /api/notices?page=0&size=10&keyword=서비스
```

향후 확장 시 변경 범위를 최소화한다.

### NFR-03 유지보수성

- Entity / DTO / Repository / Service / Controller를 분리한다.
- View / Store / API를 분리한다.
- 공통 API 오류 처리 위치를 하나로 유지한다.
- 검색/페이징 로직은 `NoticeListView` 또는 composable로 집중한다.

### NFR-04 오류 UX

- 로딩 중 표시
- API 오류 표시
- 데이터 없음 표시
- 삭제 확인
- 저장 성공 후 화면 이동

### NFR-05 CORS / 개발환경

개발 시:

```text
Vue:        http://localhost:5173
Spring:     http://localhost:8080
PostgreSQL: localhost:5432
Database:   business
Username:   postgres
Password:   1004
```

Vite 개발 서버 proxy를 사용하거나 Spring CORS를 사용한다. 하나의 방식만 선택해 중복 설정을 피한다.

## 12. Vibe Coding 원칙

### 12.1 AI에게 반드시 전달할 사실

AI에게 코드 생성을 요청할 때 다음 문장을 공통 컨텍스트로 사용한다.

```text
이 프로젝트는 공지사항 CRUD 학습 프로젝트다.

Backend:
- Java 21
- Spring Boot 4.1.x
- Gradle Groovy
- Spring Web MVC
- Spring Data JPA
- Validation
- Lombok
- PostgreSQL
- DevTools
- REST Controller

Frontend:
- Vue 3
- JavaScript
- Composition API
- <script setup>
- Vite
- Vue Router
- Pinia
- Axios
- Tailwind CSS

중요:
- 검색과 페이징은 Spring Boot에서 구현하지 않는다.
- GET /api/notices는 전체 목록을 반환한다.
- 검색과 페이징은 Vue에서 수행한다.
- 상세 조회 시 hits를 1 증가시킨다.
- 로그인/회원/권한은 현재 범위에서 제외한다.
- 불필요한 라이브러리 추가 금지.
```

### 12.2 AI 코딩 규칙

1. 기존 디렉터리와 클래스 이름을 함부로 변경하지 않는다.
2. 한 번에 하나의 기능만 수정한다.
3. 수정 전에 현재 파일 구조를 먼저 확인한다.
4. 기존 API 계약을 깨지 않는다.
5. 파일을 새로 만들 때 경로를 명시한다.
6. 완성된 파일 전체를 제공한다.
7. 생략 기호(`...`)로 코드를 생략하지 않는다.
8. 오류가 발생하면 오류 로그를 기준으로 원인을 설명하고 수정 파일을 제시한다.
9. 새로운 라이브러리는 필요성을 설명한 뒤 추가한다.
10. 검색/페이징을 서버로 이동하지 않는다.
11. `.vue` 파일은 최소 하나의 `<template>` 또는 `<script>` 블록을 포함한다.
12. 모든 Vue SFC는 `<template>`과 `<script setup>` 중심으로 작성한다.

## 14. 개발 단계별 AI 프롬프트

### Prompt 01 — 프로젝트 생성

```text
Java 21 + Spring Boot 4.1.x + Gradle + PostgreSQL 기반으로
공지사항 CRUD REST API 프로젝트를 만들어줘.

패키지는 com.kim.notice를 사용한다.

Notice 필드는:
id, title, content, author, hits, createdAt

검색과 페이징은 구현하지 않는다.
GET /api/notices는 전체 데이터를 반환한다.

Entity, DTO, Repository, Service, RestController,
Validation, 예외처리를 각각 분리하고
전체 파일의 경로와 전체 소스코드를 보여줘.
```

```text
Vue 3 + JavaScript + Composition API + <script setup> +
Vite + Vue Router + Pinia + Axios + Tailwind CSS로
공지사항 프런트엔드를 만들어줘.

Spring Boot API는:
GET /api/notices
GET /api/notices/{id}
POST /api/notices
PUT /api/notices/{id}
DELETE /api/notices/{id}

검색과 페이징은 반드시 Vue에서 처리한다.
전체 목록을 먼저 가져온 뒤
title/content/author를 검색하고
```

## 16. 인수 기준(Acceptance Criteria)

### AC-01

`GET /api/notices` 호출 시 전체 공지 목록을 200으로 반환해야 한다.

### AC-02

`GET /api/notices/{id}` 호출 시 존재하는 글을 반환하고 `hits`가 1 증가해야 한다.

### AC-03

POST로 제목/내용/작성자를 보내면 201과 생성된 Notice를 반환해야 한다.

### AC-04

PUT으로 기존 Notice를 수정할 수 있어야 한다.

### AC-05

DELETE 성공 시 204를 반환해야 한다.

### AC-06

존재하지 않는 ID 요청은 404를 반환해야 한다.

### AC-07

Vue 목록 화면에서 title/content/author 검색이 동작해야 한다.

### AC-08

Vue 목록 화면에서 10개 단위 페이징이 동작해야 한다.

### AC-09

검색 시 1페이지로 자동 이동해야 한다.

### AC-10

검색어와 페이지가 URL query에 유지되어 새로고침 후 복원되어야 한다.

### AC-11

등록/수정/삭제 후 사용자에게 적절한 성공 또는 오류 피드백이 보여야 한다.

### AC-12

Frontend `npm run build`가 성공해야 한다.

### AC-13

Backend Gradle test/build가 성공해야 한다.
